# Codex 长期省 Token 优化建议计划

## 问题对比表
| 问题 | 现象/信号 | 核心判断 | 当前结论 | 影响 |
|---|---|---|---|---|
| 回答噪音偏高 | 长会话中解释、过渡语、重复总结较多 | 输出侧约束还不够硬 | 需要把低噪音模式从“技巧”升级为“规则” | 直接推高 output token |
| 工具输出过长 | 大日志、大 diff、大 JSON 容易一次性进入上下文 | 读取策略仍偏人工自觉 | 需要更强的裁剪规则与告警联动 | 直接推高 input token |
| 长会话失忆与反复重喂 | compact 后需要重新解释背景，历史知识查找偏手工 | 已有归档，但检索层仍较轻 | 需要强化 archive 检索与结构化记忆边界 | 长线程累计 token 持续放大 |
| 大仓库理解成本高 | 仍大量依赖 rg + 读文件缩范围 | 缺少结构化代码导航层 | 应补轻量代码图谱/符号导航能力 | 容易重复扫描仓库 |
| token 花费归因不够强 | 已能看到总量、速率、热点 repo/model | 还缺操作类型归因 | 应把 usage 监控推进到 usage 归因 | 难以形成稳定节流习惯 |

## 结论对比表
| 主题 | 结论 | 依据 | 风险/边界 |
|---|---|---|---|
| 回答压缩 | 继续以 `caveman` 思路为主，但要规则化触发 | 当前仓库已有低噪音表达能力 | 过度压缩可能影响复杂问题解释质量 |
| 终端输出压缩 | 继续以 `rtk` 为主线，补“默认裁剪规则”与“高增速动作约束” | 终端输出是最稳定、最直接的噪音来源 | 规则过硬会影响极少数诊断场景的证据完整性 |
| 外部上下文 | 优先强化 `archive-search` 和归档索引，不急着引入重型向量库 | 现有沉淀链已成型，检索增强投入产出高 | FTS/索引需要控制复杂度，避免新维护负担 |
| 结构化代码导航 | 先调研 `code-review-graph` / `token-savior`，后决定是否落地轻量本地索引 | 大仓库扫描成本高，当前能力空缺明显 | 直接引入重系统会过早复杂化 |
| 可观测与归因 | `usage-tail` 已具备生产形态，下一阶段应补“为什么烧 token” | 总量、速率、热点已经可见 | 归因规则若太粗糙，可能给出误导建议 |

## 当前资产基线
| 资产 | 当前状态 | 作用 | 后续方向 |
|---|---|---|---|
| `rtk` | 已接入主工作流 | 压缩 shell 输出 | 继续强化默认裁剪规则 |
| `usage-tail` / `usage-report` | 已完成轻交互 TUI | 实时观测 token 消耗 | 补操作类型归因与快照沉淀 |
| `session-wrap` / `knowledge-archive` | 已形成会话收口链 | 归档高价值知识 | 提高归档后检索与回用效率 |
| `memory-curator` | 已有 Phase 1/2/3 边界 | 管理长期记忆污染风险 | 补更清晰的晋升标准 |
| `archive-search` | 已具备基础检索能力 | 从归档与规则中找历史结论 | 补索引化、过滤与结果质量 |
| `caveman` | 已安装可用 | 压缩回答输出 | 与 token 风险告警联动 |

## 分层优化路线

### Phase 1：规则硬化与低成本提效
目标：先把“少说、少读”从经验变成默认行为。

| 事项 | 动作 | 预期收益 | 验收标准 |
|---|---|---|---|
| 回答压缩规则化 | 在 `AGENTS.md` 明确高 token 风险时的低噪音输出策略 | 降低长会话 output token | 高风险线程下输出更短、更少重复解释 |
| 工具输出裁剪默认化 | 明确大日志 / 大 diff / 大 JSON 的裁剪规则 | 降低 input token | 新任务默认不再直接喂原始大输出 |
| usage 告警联动动作建议 | 告警直接落到下一步读取策略建议 | 提高节流执行力 | 出现 HOT/CRITICAL 时建议可执行 |
| 归档检索入口稳定化 | 将 `archive-search` 纳入常用工作流 | 降低重复解释背景 | 常见历史结论可快速命中 |

### Phase 2：外部上下文检索层增强
目标：让沉淀真正可搜索、可复用，而不是仅仅存档。

| 事项 | 动作 | 预期收益 | 验收标准 |
|---|---|---|---|
| 归档索引化 | 评估并引入 SQLite FTS5 或等价轻量索引 | 提高大规模归档检索效率 | 查询速度与命中质量稳定提升 |
| 结构化 metadata | 为 archive 条目补 topic/date/source/tags 过滤 | 降低检索噪音 | 查询结果更聚焦 |
| 检索回链 | 在重要工具中加入“去哪里看历史结论”的提示 | 提高沉淀复用率 | 告警或总结可直接指向归档结果 |

### Phase 3：结构化代码导航层
目标：减少大仓库下的全仓扫描与重复读文件。

| 事项 | 动作 | 预期收益 | 验收标准 |
|---|---|---|---|
| 方案调研 | 对 `code-review-graph`、`token-savior` 做小规模 PoC | 明确是否适配当前工作流 | 得出引入/不引入结论 |
| 轻量实现优先 | 若落地，先做本地 SQLite + 符号/调用关系最小集合 | 控制复杂度 | 可支持符号定位与影响范围判断 |
| 与现有工具集成 | 与 `usage-tail`、`archive-search`、AGENTS 规则衔接 | 形成统一入口 | 调用链分析不再完全依赖手工读仓库 |

### Phase 4：归因与节流闭环
目标：从“看到 token 花了多少”升级到“知道为什么花掉了”。

| 事项 | 动作 | 预期收益 | 验收标准 |
|---|---|---|---|
| 操作类型归因 | 区分日志读取、diff、全仓扫描、长线程滚上下文等主要来源 | 找到主要浪费点 | 报告可解释主要消耗来源 |
| 快照沉淀 | 将 usage 快照写入稳定时序文件 | 支持日报、周报、回放 | 可按日/仓库/模型回看趋势 |
| 策略回路 | 高风险模式命中后，回写到工作流建议中 | 形成行为闭环 | 重复问题出现频率下降 |

## 推荐优先级
| 优先级 | 项目 | 原因 |
|---|---|---|
| P0 | 回答压缩规则化 + 输出裁剪默认化 | 收益最快，改动最小 |
| P0 | `archive-search` 持续强化 | 已有基础，最容易形成复用 |
| P1 | usage 归因能力 | 有助于从观测走向治理 |
| P1 | 结构化代码导航 PoC | 对大仓库收益大，但需先调研 |
| P2 | 重型外部记忆或向量检索 | 复杂度高，当前不急 |

## 不建议当前阶段做的事
| 项目 | 原因 |
|---|---|
| 一次性引入多个重型 MCP / 向量数据库系统 | 复杂度和维护成本会先失控 |
| 同时接入多套相似 token 仪表盘 | 容易重复建设、指标冲突 |
| 把 archive、memory、agent memory 自动双写 | 容易污染长期记忆边界 |

## 关键结论
1. 当前 `codex` 体系已经具备“少说、少读、可沉淀”的基础骨架，下一阶段重点不是扩张工具数量，而是压实规则、检索与归因闭环。
2. 最值得优先做的不是重型新系统，而是把 `caveman`、`rtk`、`usage-tail`、`archive-search` 这四条线打通。
3. 结构化代码导航层值得重点研究，但应先做 PoC，再决定是否正式纳入长期体系。

## 后续建议
| 项目 | 说明 |
|---|---|
| 规则落地 | 将高 token 风险下的低噪音输出与读取裁剪策略写入项目规则 |
| 检索增强 | 为 `archive-search` 增加索引和过滤能力 |
| 归因增强 | 为 `usage-tail` 增加“主要消耗来源”分析 |
| 结构导航调研 | 单独产出一份 `code-review-graph / token-savior` 适配评估 |
