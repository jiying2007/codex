# 小团队直接 CLI 交付与长期资产

## 决策

日常主线是 Codex CLI + 已安装的 ADK 资源 + 项目 Git/CI/审查 + Knowledge Hub。WorkBuddy 是可选需求/协作入口；Claude 等运行时按需使用，未经对应真实证据不得声明具备等价替代资格。Digital Worker 只作为显式选择的领域/正式证据集成保留，不是日常开发依赖。engineering-platform 是另一套独立方案，不在本链路迁移或合并。

## 谁负责什么

- ADK：通用方法、Skill/Workflow、资产验证和发布；不接管项目运行状态或产品放行。
- Codex 资源发行：版本固定、build/plan/apply、drift/rollback；不共享成员认证、私有配置或 session。
- 项目：需求与验收、源码、测试/设备事实、代码审查与接受决定；复用 Issue/PR/现有项目记录，不另建一套 Work/Run。
- Knowledge Hub：来源清楚的知识与 reviewing candidate；检索结果不是批准，未确认结论不自动提升 active。
- llm_agent：研究、评估与改进建议；不进入每次任务的执行前置链。
- Digital Worker：可选集成、已有 Pilot/R2 与历史证据；不向所有日常任务传播其资格门禁。

## 日常任务闭环

1. 在现有项目记录中确定目标、变更范围、风险和验收标准。
2. 使用安装好的资源直接开发；项目事实从源码/测试系统读取，相关历史知识通过 Knowledge Adapter 查询。
3. 构建、测试并保存准确版本与原始结果；需要设备/HIL 的结论不能用主机单元测试代替。
4. 由适当责任人接受结果；高风险发布、设备操作及安全变更继续执行项目权限和审批。
5. 在同一个 Issue/PR 记录结果、证据入口、未验证项与接受人。可复用经验形成 Knowledge candidate；没有可复用结论时明确说明，不强制制造归档。

以上是交付要求，不代表 Bootstrap 自动执行或验证了每一步。Skill 是执行指导，脚本/CI/权限才实施可强制检查。没有 Digital Worker 不等于取消任何项目交付条件。

## 资源发布与升级

普通成员只消费经过审查的资源发行版本，不需要克隆全部维护仓。维护者使用现有 build/doctor/plan/apply dry-run/回滚链路；不要在正在执行的任务中无提示更换资源。团队发行使用 ADK 的 `docs/runbooks/codex-team-runtime-distribution.md`；本仓自身资源维护使用 README 的计划式安装流程，两者不要混成一条不存在的命令。

ADK 发布版本、Codex vendored 版本和成员 live 版本是三个不同事实。升级必须校验 exact source identity 与回归；不能只改版本字符串、覆盖旧 evidence 或宣称所有成员已更新。

## 中断与恢复

恢复前核验项目分支/HEAD、工作区改动、任务记录、已完成测试和正在执行的命令。聊天恢复不是工程检查点；不要因会话丢失重跑刷写/发布。旧验收只适用于当时的被验对象，后续实质修改需要相应重新验证。

## 选择性保留 Digital Worker 资产

通用方法经去重与效果验证后进入 ADK；项目条件回到项目；知识与来源进入 Hub；已有正式证据保持原始身份可追溯。不要整包合并 Digital Worker，也不要为了降低仓库数量重写其历史。现有 L2/receipt/R2 作为可选路径保留，其缺项只限制相应资格声明。

## 验收而非口头宣称

仓库单元/合同测试验证日常模式不依赖 Digital Worker，以及正式模式不静默降级。团队现场还需分别验证：新成员安装与真实 Skill 使用；真实缺陷/功能验收；中断恢复；资源升级回退；另一任务的知识复用。静态或合成 fixture 不得充当上述现场证据。

本轮没有自动修改成员 `~/.codex`、没有部署内部团队发行仓、没有刷新 ADK vendor pin、没有把 R2 或产品资格改成 PASS。上述状态必须以相应执行回执为准。
